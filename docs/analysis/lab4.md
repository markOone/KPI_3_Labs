# Лабораторна робота 4: Синхронна та асинхронна комунікація між компонентами

## Резюме змін порівняно з Лабораторною 3

У попередній лабораторній роботі система працювала відповідно до лінійної архітектури: контролер → handler → домен → репозиторій. Усі операції виконувались синхронно в одному потоці.

У Лабораторній 4 ми розширили архітектуру, виділивши **допоміжний компонент Notification Service** та реалізувавши два способи комунікації з ним:
1. **Синхронний** - прямий виклик сервісу
2. **Асинхронний** - публікація подій через Event Bus

Ця розділення дозволило нам дослідити переваги та недоліки кожного підходу в контексті реальних систем.

## Вибір побічної операції

Виділено **Notification Service** як основний допоміжний компонент, який відповідає за відправку повідомлень користувачам при важливих подіях:

- **OrderCreatedEvent** - коли замовлення успішно створене
- **OrderCancelledEvent** - коли замовлення скасоване

Цей вибір логічний, оскільки:
- Нотифікація користувача є окремою відповідальністю, що не впливає на основну бізнес-логіку замовлення
- Може мати своє время виконання та довготривалість
- У реальній системі могла б бути замінена на іншу реалізацію (SMS, push-notification, тощо)

## Порівняння синхронного та асинхронного підходів

### 1. Час відповіді API

#### Синхронний підхід:
```
POST /checkout
├─ Отримати кошик
├─ Валідувати товари
├─ Створити замовлення в БД
├─ Зменшити запас товарів
├─ **Відправити email (ОЧІКУВАННЯ)**
└─ Повернути результат (ЗАГАЛЬНИЙ ЧАС = основна операція + нотифікація)
```

**Спостереження:**
- Час відповіді API включає час відправки email
- Якщо email-сервіс повільний (2-3 сек), користувач чекає
- Загальний час: ~500ms (логіка) + ~2500ms (email) = 3000ms

#### Асинхронний підхід:
```
POST /checkout
├─ Отримати кошик
├─ Валідувати товари
├─ Створити замовлення в БД
├─ Зменшити запас товарів
├─ **Опублікувати подію (миттєво в памяті)**
└─ Повернути результат (ЗАГАЛЬНИЙ ЧАС = лише основна операція)
```

**Спостереження:**
- Час відповіді API залежить лише від основної логіки
- Email відправляється в фоні через Event Bus
- Загальний час: ~500ms (логіка) + ~5ms (публікація) = 505ms
- **Користувач одержує відповідь на 85% швидше**

### 2. Поведінка при збоях

#### Синхронний підхід:

**Сценарій:** Email-сервіс недоступний
```python
async def handle(command):
    order = create_order(...)
    await notification_service.send_order_created(order, user)  # Падає!
    return order.id
```

**Проблеми:**
- Замовлення вже створене, але користувач отримує помилку
- Потрібно вирішити: відкотити замовлення чи ігнорувати помилку?
- Якщо відкотити - користувач бачить помилку, але замовлення насправді створене в БД
- Якщо ігнорувати - користувач отримує результат, але без нотифікації
- **Потенційна невідповідність стану між API клієнтом і БД**

#### Асинхронний підхід:

**Сценарій:** Email-сервіс недоступний
```python
async def handle(command):
    order = create_order(...)
    await event_bus.publish(OrderCreatedEvent(...))  # Завжди успішна!
    return order.id  # Користувач отримує результат
```

**Переваги:**
- Замовлення завжди створюється успішно
- Користувач отримує гарантовану відповідь
- Якщо обробник подій падає - він просто не обробляється (або повторюється пізніше)
- **Чітка розділеність: основна логіка завжди працює, побічні операції можуть збиватися**

**Спостереження:** Збій в асинхронному підході легше розглянути як проблему моніторингу, а не користувацької помилки.

### 3. Зв'язаність між компонентами

#### Синхронний підхід:

```python
class ProcessCheckoutCommandHandler:
    def __init__(self, ..., notification_service: NotificationService):
        self.notification_service = notification_service
    
    async def handle(self, command):
        order = create_order(...)
        # Handler ЗНАЄ про NotificationService!
        await self.notification_service.send_order_created(order, user)
```

**Аналіз:**
- Handler явно залежить від `NotificationService`
- Якщо змінити контракт `NotificationService` - потрібно змінити Handler
- Якщо додати нову нотифікацію (SMS, push) - потрібно модифікувати Handler
- **Висока зв'язаність**: Handler "знає" про конкретну реалізацію

#### Асинхронний підхід:

```python
class ProcessCheckoutCommandHandler:
    def __init__(self, ..., event_bus: EventBus):
        self.event_bus = event_bus
    
    async def handle(self, command):
        order = create_order(...)
        # Handler просто публікує подію, не знаючи хто її обробляє!
        await self.event_bus.publish(OrderCreatedEvent(...))
```

**Аналіз:**
- Handler залежить лише від `EventBus` - загального механізму доставки
- Handler не знає про реалізацію нотифікацій
- Нові обробники подій можна додавати без змін у Handler:
  ```python
  # Додаємо SMS-нотифікацію просто підпиской
  event_bus.subscribe("order.created", SMSNotificationHandler())
  ```
- **Низька зв'язаність**: Handler публікує факт, а не виконує побічну операцію

### 4. Обробка помилок в синхронному потоці

#### Проблема: Синхронні виклики можуть зупинити основну операцію

У попередній версії помилка при відправці нотифікації зривала весь процес:
```python
async def handle(command):
    order = create_order(...)
    await self.notification_service.send_order_created(order, user)  # Якщо упасть - замовлення створене, але клієнт отримує помилку!
    return order.id
```

#### Рішення: Try-catch обгортання побічних операцій

**Нова реалізація в синхронному режимі (lines 95-98, 175-178):**
```python
else:
    try:
        await self.notification_service.send_order_created(created_order, user)
    except Exception as e:
        logger.error(f"Failed to send synchronous notification for order {created_order.id}: {e}")
```

**Переваги цього підходу:**
- ✅ **Гарантована успішність основної операції**: замовлення створене, незалежно від статусу нотифікації
- ✅ **Логування помилок**: є інформація для debug та моніторингу
- ✅ **Graceful degradation**: користувач отримує результат без помилки, навіть якщо нотифікація не відправилася
- ✅ **Вирішує парадокс**: замовлення гарантовано в БД, і користувач це знає

**Це наближує синхронний підхід до надійності асинхронного**, адже основна операція більше не залежить від побічних ефектів.

### 5. Складність реалізації та тестування

#### Синхронний підхір:

**Тестування:**
```python
async def test_checkout_sync():
    mock_notification = AsyncMock()
    handler = ProcessCheckoutCommandHandler(..., notification_service=mock_notification)
    
    await handler.handle(command)
    
    # Просто перевіряємо, що сервіс був викликаний
    mock_notification.send_order_created.assert_called_once()
```

**Простота:**
- Легко тестувати - можна mockати сервіс
- Легко налагоджувати - весь потік виконання в одному потоці
- **Реалізація проста**: прямий виклик функції

**Недоліки:**
- Складно моделювати збої (потрібно mock викидати виключення)
- Важко тестувати поведінку при timeout
- Все залежить від mock'ів в тестах

#### Асинхронний підхід:

**Тестування:**
```python
async def test_checkout_async():
    event_bus = InProcessEventBus()
    published_events = []
    
    async def track_events(event):
        published_events.append(event)
    
    event_bus.publish = track_events
    handler = ProcessCheckoutCommandHandler(..., event_bus=event_bus)
    
    await handler.handle(command)
    
    # Перевіряємо, що подія була опублікована
    assert len(published_events) == 1
    assert isinstance(published_events[0], OrderCreatedEvent)
```

**Складність:**
- Потрібно розуміти Event Bus механізм
- Потрібно реалізувати Event Handlers
- Тестування обробників потребує більше коду

**Переваги:**
- Легко тестувати ідемпотентність (чи обробник правильно обробляє дублікати подій)
- Можна тестувати множинні обробники однієї події
- Більш реалістичне моделювання асинхронних операцій

## Рекомендація для production-системи

**Рекомендований підхід: Асинхронний (Event-driven) з наступними уточненнями:**

### Аргументи:

1. **Масштабованість**: 
   - Синхронна система впаде під навантаженням, якщо нотифікаційна система почне працювати повільніше
   - Асинхронна система може масштабуватися незалежно

2. **Надійність**:
   - Основна операція гарантована відрізана від побічних ефектів
   - Можна додати retry-логіку для Event Bus без впливу на користувача

3. **Еволюція**:
   - Легко додавати нові обробники без модифікацій основного коду
   - Можна експериментувати з новими типами нотифікацій

### Проте з умовами:

1. **Забезпечити доставку подій**:
   - In-process Event Bus достатньо для простих систем, але для production потрібен брокер (RabbitMQ, Redis, Kafka)
   - Потрібна гарантія доставки "at-least-once"

2. **Обробити ідемпотентність**:
   - Кожен обробник повинен бути ідемпотентним (обробляти дублікати безпечно)

3. **Моніторити нотифікації**:
   - Додати метрики для відстеження необроблених подій

## Ідемпотентність обробників

### Проблема: Дублікати подій

Якщо брокер подій доставить одну й ту саму подію двічі (може статися при перезавантаженні):

**Синхронний підхід:** 
- Користувач отримає два email'и - **проблема!**

**Асинхронний підхід:**
```python
async def handle_order_created(event):
    order = await order_repository.get_by_id(event.order_id)
    user = await user_repository.get_by_id(event.user_id)
    
    # Перевіряємо, чи вже було відправлено
    notification = await notification_repository.get_by_order_and_user(
        event.order_id, event.user_id
    )
    
    if notification:
        return  # Вже обробили!
    
    # Відправляємо email та записуємо в БД
    await send_email(user.email, ...)
    await notification_repository.create(Notification(...))
```

**Наші тести перевіряють:**
- `test_event_bus_idempotency()` - що обробник отримує обидва дублікати
- `test_event_bus_multiple_subscribers()` - що множинні обробники отримують одну подію

## Висновок

Асинхронна комунікація через Event Bus залишається кращим вибором для production-систем завдяки масштабованості та еволюційності. Однак з введенням proper error handling (try-catch обгортанням) синхронний підхід набуває надійності та може використовуватися для:

- **Менших систем** з передбачуваним навантаженням
- **Критичних операцій**, де простота налагодження важлива
- **Фаз розробки**, коли архітектура ще не остаточно визначена

**Гібридний підхід:** часто найкраще використовувати асинхронність для важких операцій (email, обробка платежів) та синхронність для легких (логування, кешування).

Ключова закономірність: **незалежно від синхронного чи асинхронного підходу, основна операція ніколи не повинна падати через побічні ефекти** — для цього слугують try-catch блоки та Event Bus isolation.
